# 07 — 腾讯系 11128 修复（WorkBuddy / CodeBuddy 渠道校验与内容风控）

> 移植性质：**差异合并**（来源 `deepseek-harness-codearts` HEAD 早已有这两套适配，
> 本项目移植基线 `3611a62` 时**没有一并搬过来**）。
>
> 写作时点：2026-10-19。来源侧权威实现：
> `src/openai-gateway/tencent-fingerprint.ts` + `src/buddy-adapter.ts` 的 `send()`。

## 0. 症状

经本网关访问 `workbuddy`（WorkBuddy 国际版）或 `buddy`（CodeBuddy 中国版）时，
上游返回：

```json
{"error":{"message":"[400]: {\"code\":11128,\"msg\":\"request illegal\", ...}",
 "type":"invalid_request_error","code":"bad_request"}}
```

## 1. ⚠️ 首要纪律：`code 11128` 有多个子原因，**必须看 `msg`**

| `msg` | 归类 | 判据 | 修法 |
|---|---|---|---|
| `request illegal` | **渠道校验**（**按账号**生效） | 三枚 `X-Conversation-*` 头必须**同时存在且非空** | §2 |
| `conversation id missing` | 同上（同族另一种措辞） | 同上 | §2 |
| `Illegal API invocation from an unapproved channel` | **内容级风控** | `system` / `assistant` 正文含客户端模板句 | §3 |
| `first message is not system prompt` | 结构校验 | wire 首条必须是 `role:"system"` | 本项目早已实现（见 `shared/message-shape.ts`） |

⚠️ 三族的 `displayMsg` / `displayTips` **逐字相同**（都是「请求被拦截」
「没通过渠道校验，可能不是官方客户端发出的」）⇒ **绝不能拿 `displayTips` 判原因**。

⚠️ 另有一处易踩的判据冲突：`request illegal` 这句措辞**同时被 11140（账号级安全
策略拦截）使用** ⇒ 分类判据必须**同时**按 `code` 精确等于 `11128` 收窄，
否则会把「带三头就能用」的报文判成账号级拦截（来源仓库记录过这个真实缺陷：
误判后写 30 分钟冷却、烧掉整池）。

## 2. 修复一：补齐 `X-Conversation-*` 三枚头

### 判据（来源实测，非推断）

腾讯网关对**部分账号**做「渠道校验」，三枚官方会话头必须同时存在且非空：

- **不校验值语义**：三枚同值 / 各自不同 / 填 `abc-123` **全部放行**；
- **不要求三者一致**；
- **填空串 = 缺**（仍 400）；
- **逐请求判定**：带三头 → 紧接无头，`200 → 400` 可来回切（**非封禁、非状态粘性**）；
- **内容无关**：换 system、换最简 body 仍 400；
- 仅补一枚仍 400（必须三枚齐全）。

⚠️⚠️ **生效范围「按账号」**（来源实测 2/5、3/5 两种比例）⇒「某些账号不带三头也 200」
**不能**用来论证「三头不必发」。这也是本缺陷长期未暴露的原因：换机器/换账号就复现不了。

⚠️ 语义：三枚是**逐请求一次性 id**，不是会话身份。来源实测上游**不做**跨轮状态机
（同一 `prompt_cache_key` 连发三轮、每轮换三头值，上游 3/3 接受）。

### 实现

`src/providers/tencent-conversation-headers.ts`：

```ts
applyTencentConversationHeaders(headers: Headers): Headers
// 一次生成一组 32 位 hex，一起写入：
//   X-Conversation-ID / X-Conversation-Request-ID / X-Conversation-Message-ID
```

接线点：`src/providers/buddy-adapter.ts` 的 `send()`，在
`headers.set(HTTP_HEADER_PRODUCT, ...)` 之后、`User-Agent` 覆盖之前。

> **为什么在 `send()` 而不是更上游**：`send()` 是唯一真正发出 chat 请求的地方，
> 换号重试、饱和退避重试都汇聚到它 ⇒ 一处接线覆盖全部出站路径。
> ⚠️ 来源仓库登记过「旁路漏接线」的事故（`buddy-growth.ts` 两条直发请求不走主链路），
> 本项目没有那两条旁路，故只需改这一处；**将来若新增直发 `/v2/chat/completions`
> 的代码，必须同样调用本函数**。

## 3. 修复二：内容级指纹改写

### 已登记的三条（`src/providers/tencent-fingerprint.ts`）

| 指纹 | 来源 | 被拦位置 |
|---|---|---|
| `Main branch (you will usually use this for PRs)` | ZCode 注入的 git 状态行 | `system` / `assistant` |
| `You are Claude Code, Anthropic's official CLI for Claude` | Claude Code 身份句 | `system` / `assistant` |
| `To give feedback, users should report the issue at https://github.com/anthropics/claude-code/issues` | Claude Code 反馈句（**每轮必带**） | `system` / `assistant` |

### 三条不能违反的约束（逐条实测得出）

1. **只改 `system` 与 `assistant` 正文**，其余一概不碰：
   `user` / `tool` 结果 / `reasoning_content` / `tool_calls[].arguments` 实测**都不拦**。
   改它们换不来放行，却会篡改用户原话、工具输出（要回读给模型看的证据）与模型思考。
   ⚠️ 反向也要守住：**别把 `assistant` 这格简化掉** —— 会话历史里的 assistant 正文
   含指纹是**必然**：用户让 agent 排查风控问题时，模型会先 `read` 记录该指纹的文档
   （tool 结果，不拦），再逐字复述进自己正文（拦）⇒ 那条消息从此每轮原样重放
   ⇒ 「这个 provider 从此每轮都失败，换任何腾讯系模型都一样」（跟会话走，不跟模型走）。
2. **改写所有 `system` 消息**，不只 `messages[0]`（非首位 system 同样被拦）。
3. **大小写不敏感的精确字面量**，不做正则/关键词泛化：
   全小写/全大写都被拦（必须带 `i`）；但「只差一个词」「多一个空格」都放行（不能泛化）。
4. **无指纹文本必须逐字符不变** —— 腾讯侧按前缀缓存，无谓重建字符串会白吃缓存命中。
5. **`find` 长度只能逐条实测**：反馈句那条实测「砍掉前半/后半即放行」⇒ 必须写整句；
   写短了等于**空跑**（登记了却仍每轮 400），症状极具误导性。

### 接线点（⚠️ 四处，缺一即漏）

`serializeMessages` 是**独立函数**（不是类方法），故 `provider` 必须作为**第三参数**传入：

| 位置 | 说明 |
|---|---|
| `serializeMessages` 的 `assistant` 分支 | 只改正文，**不动** `reasoning` / `tool_calls.arguments` |
| `serializeMessages` 的 `system` 分支 | 所有 system 消息 |
| `stream()` 里 `options.system` 的 `unshift` | ⚠️ **第四个产出点**：它绕过 `serializeMessages`，漏掉等于「走 messages 的会话被救了、走 system 的会话照样被拦」 |
| — | `user` / `tool` 分支**刻意不改** |

## 4. 实测证据（2026-10-19，本机真实端点）

用**构建产物 `dist/`** 的 `BuddyAdapter` 驱动真实账号（`www.workbuddy.ai`，`fast-model`）：

```
[minimal]
  -> HTTP 200 OK
  outbound conv headers: X-Conversation-ID=✓ X-Conversation-Request-ID=✓ X-Conversation-Message-ID=✓

[assistant history w/ fingerprint]
  -> HTTP 200 OK
  outbound conv headers: X-Conversation-ID=✓ X-Conversation-Request-ID=✓ X-Conversation-Message-ID=✓
  assistant body rewritten: ✓

[system w/ fingerprints]
  -> HTTP 200 OK
  outbound conv headers: X-Conversation-ID=✓ X-Conversation-Request-ID=✓ X-Conversation-Message-ID=✓
```

修复前，`assistant history w/ fingerprint` 这一格稳定回
`400 code=11128 "Illegal API invocation from an unapproved channel"`
（在 9router 与 codearts 两侧均实测复现，见 9router 的
`docs/TENCENT_11128_FIX.md` §4）。

⚠️ **诚实标注**：`request illegal`（渠道校验）这一格**未能复现** —— 本机 11 个账号
（10 个 codebuddy-cn + 1 个 workbuddy）做 `0/1/2/3` 头全矩阵消融**全部 200**，
说明这些账号都不在「要求三头」的白名单里。本项只验证了**结构性差异**
（修复前 0/3 → 修复后 3/3），判据本身来自来源仓库的跨账号实测。

## 6. 排障指引

1. **先取失败报文的 `msg`**，不要只看 `code`，更不要看 `displayTips`。
2. `request illegal` / `conversation id missing` ⇒ 渠道校验方向：
   - 核对三枚 `X-Conversation-*` 是否同时存在且非空（打印头名即可，**不要打印 token**）；
   - **优先核对「那个账号」** —— 按账号生效，别按内容方向排查。
3. `Illegal API invocation from an unapproved channel` ⇒ 内容方向：
   - 拿完整请求体逐条消息二分送检，定位到具体消息与角色；
   - 命中新模板句时往 `CONTENT_FINGERPRINTS` 加一行 + 一条用例；
   - ⚠️ 加之前**必须实测最小充分串**（砍掉前后半是否仍拦），否则会空跑。
4. `first message is not system prompt` ⇒ 检查 wire 首条角色。
