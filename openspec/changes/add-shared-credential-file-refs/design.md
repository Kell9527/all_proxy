# Design

## Context

参见 `proposal.md` 的 Why 与实测证据。核心约束如下。

**一次性 refresh_token 的语义**：`codearts` / `trae` / `raccoon` 的 refresh token 用一次即作废（实测 raccoon 旧 token 再用返回 `refresh_conflict`；华为返回 `STS5.1806 the refresh token has been used`）。因此「持有一份缓存副本」在这种 provider 上是**结构性错误**：副本迟早会因为别人刷新而变成死 token。

**现状的竞态面**（已逐处核实）：

| 路径 | 位置 | 触发条件 |
|---|---|---|
| 临期刷新 | `raccoon-adapter.ts:217` 等适配器 | 请求前发现 `isRaccoonExpired` |
| 401/403 重试刷新 | `raccoon-adapter.ts:298` 等 | 上游拒绝 |
| 定时任务 | `refreshDueAccounts` | 启动时 + 每小时 |
| 请求路径重写 | `index.ts` 的 `wiringRefresh` | 适配器回调 |

这四条会在同一时刻碰到同一账号，而**全仓此前没有任何单飞/互斥**。

**另一处真实缺陷**：`wiringRefresh` 用 `pool.getAvailableAccount(provider, '')` 取凭据，即「该 provider 的首个可用账号」，而非适配器**实际选中**的那个。多账号时它会刷新错误的对象 —— 用户正在用的账号依旧过期（请求继续失败），而一个无关账号的 refresh_token 被白白轮换。适配器的调用时序其实已经给出了正确答案（`resolveCredential` 里通过 `recordCurrentAccount` 记录了选中账号）。

**参考实现**：`D:\Project\go\token_proxy\xiaohuanxiong2api` 已验证的做法 —— `accounts.json` 存 `authFile` 路径，`readCredentials()` 每次读文件、`doRefresh()` 刷新前重读、写回用临时文件 + rename + 0600。

## Goals / Non-Goals

**Goals：**

- 让同一批凭据被多个消费者共享时**不再互相作废**。
- 消除本服务内部对同一凭据的并发刷新。
- 修掉「刷新刷到别的账号」这个真实缺陷。
- 默认零行为变化：不绑定的账号完全按既有方式工作（含「用户没装官方客户端也能用」）。
- provider 代码维持零文件系统访问（既有架构约束）。

**Non-Goals：**

- **不做跨进程文件锁**。两个网关恰好同时临期刷新时，仍可能有一方失败（服务端拒绝或返回另一份）。这不是正确性缺口：失败方下次 `resolve` 会读到获胜方写回的新 token，随即成功。做跨进程锁需要引入锁文件协议与超时回收，复杂度远超收益，且无法约束官方客户端。
- 不把官方客户端的路径**设为默认值**（那会重新引入「客户端退出即删除 auth.json」的依赖）。
- 不改动 10 个 provider 的协议实现与登录流程。

## Decisions

### D1：能力做在凭据存储层，而非 provider 层

**选择**：`FILE:` 前缀的解析与读写全部落在 `src/pool/store.ts`（通用能力），`src/providers/raccoon*.ts` 不新增任何文件访问。

**理由**：`raccoon-client-independence.spec.ts` 用源码扫描锁死「provider 实现不得依赖客户端文件」，其**真实意图**是「不得把客户端数据当运行时前置条件」。把能力放在存储层后：provider 代码仍零文件访问、默认仍是内置存储、是否使用外部文件完全由用户显式绑定决定 —— 意图完整保留，而能力对 10 个 provider 通用。

**替代方案**：在 `raccoon-adapter.ts` 里直接读 `~/.box-agent/config/auth.json`。被否决：会打破既有约束、只对一个 provider 生效、且默认依赖客户端（客户端退出即失效）。

### D2：用 `FILE:` 前缀，而不是新增 `credentialFile` 字段

**理由**：`credentialRef` 本就是字符串，在 `state.json` / 备份文件 / 管理端之间原样透传；加前缀后**无需改任何 schema**。新增字段则要改十几处读 `credentialRef` 的地方（账号池、备份、管理端、各 auth 服务），还要定义两个字段并存时的优先级。

**安全性**：`parseCredentialRef` 只认前缀，**不做**「看起来像路径就当文件」的猜测 —— 内置 ref 形态多样（`*_ACCOUNT_*`、`*_ACCESS_TOKEN`），猜测规则迟早误判。

### D3：`resolve` 实时读盘、不缓存

**理由**：这正是机制本身。共享文件的价值就是「别人写了新的，我下次就读到」。加一层缓存即退化成死副本，且**不会报错**，只表现为「账号又过期了」—— 最难查的回归类型。已用测试锁死（`credential-file-ref.spec.ts` 的「外部改动立即反映」）。

**代价**：每次请求多一次文件读（本地磁盘，微秒级，可忽略）。

### D4：`unset` 对文件引用是无操作

**理由**：那个文件可能被官方客户端或其它网关共享，删除会破坏本服务**之外**的凭据，且 refresh token 一次性、无法恢复。摘除引用由账号池从索引里移除条目完成。

**配套**：`removeAccount` 照常摘除条目但不删文件；「解绑」走 `rebindCredential`，把内容**转存**到内置 ref 后再改指针（直接摘除会让用户莫名丢凭据）。

### D5：换绑时「文件已有内容」以文件为准

**理由**：典型情形是绑到一个官方客户端已写好的文件。若用旧凭据覆盖它，等于把别的消费者刚刷出来的 token 抹掉 —— 正是本机制要避免的事。故 `rebindCredential` 先探测新 ref，**有内容就不迁移**（`migrated: false`）。

### D6：单飞按 `credentialRef` 为键

**理由**：多个账号条目可以指向同一个凭据文件（共享同一份 token），那种情形同样必须互斥。按账号 id 单飞会漏掉这一层。

**失败不缓存**：`finally` 立即移除条目。若缓存 rejected Promise，一次失败会让账号在进程生命周期内再也刷不动（静默失效）。

### D7：定时任务改为并发执行

**理由**：这不是性能优化，而是**单飞能否生效的前提**。原实现逐个 `await`，前一个结束后锁已释放，后一个会真的再刷一次 —— 两个账号指向同一文件时把一次性 token 白轮换一次。并发后单飞才能把它们合并成一次上游请求。

**配套**：刷新结果由单飞 Promise **返回**，各条目再各自更新自己的 `expiresAt`。若在单飞体内直接更新池，后到的条目会漏掉 `expiresAt`（界面显示旧有效期，甚至被判成仍临期而反复续期）。

### D8：备份内联文件内容

**理由**：备份必须自包含 —— 换机器恢复时那个外部文件可能根本不存在（它可能属于官方客户端的安装）。故导出时按 ref 键内联内容；导入时按 ref 语义写回**原路径**。路径不可写则跳过并记入 `skipped`（账号条目照常导入、表现为「凭据缺失」），**不降级**写进内置存储 —— 那会造成一份与共享文件分叉的副本，正是本机制要消灭的东西。

### D9：管理端路径脱敏

**理由**：绝对路径含本机用户名，管理端可能被截图或投屏。展示保留尾部两段（`…/config/auth-a.json`）足以让用户认出是哪个文件；完整 ref 留在 `title` 里供排查复制。

## Risks / Trade-offs

- **每次请求多一次文件读** → 本地磁盘读取，微秒级；换来的是「不会持死副本」，值得。
- **两个网关同时临期刷新仍可能失败一次** → 失败方下次 `resolve` 读到新 token 后成功；不引入跨进程锁（见 Non-Goals）。
- **用户绑到不存在的路径** → 该账号表现为「凭据缺失」；绑定接口返回 `readable: false`，管理端明确提示，不让用户对着空目录猜。
- **锁文件/权限在 Windows 上不可靠** → `chmod 0600` 在 Windows 基本无效，与参考实现一致地忽略失败；凭据保护主要靠文件系统 ACL。
- **`FILE:` 是保留前缀** → 理论上某个 provider 若真用 `FILE:` 开头的内置 ref 会冲突。已评估：现有 10 个 provider 的 ref 常量全部是 `*_ACCOUNT_*` / `*_ACCESS_TOKEN` 形态，无冲突。
